  三、先解释 raw 中间样本 是怎么从原始轨迹来的
  核心函数在：

  - process_data/trajectory_coldstart/stepify.py:82

  ### 第 1 步：选哪些原始轨迹

  在 process_data/trajectory_coldstart/common.py:37 里，会从 classified_by_f1 收集轨迹。

  默认只选：

  - 2_medium_f1_50-100
  - 3_perfect_match_100

  默认长度桶：

  - short_lt100k
  - medium_100k_300k

  这些默认值定义在：

  - process_data/trajectory_coldstart/common.py:8
  - process_data/trajectory_coldstart/common.py:9

  所以 raw 中间样本 不是全量原始数据，而是先经过“按质量桶和长度桶筛选”的。

  ———

  ### 第 2 步：把一条 trajectory 切成很多 step

  原始轨迹长这样：

  - system
  - user
  - assistant + tool call
  - tool result
  - assistant + tool call
  - tool result
  - ...
  - assistant + task_done

  在 process_data/trajectory_coldstart/stepify.py:106 里，代码会遍历每个 llm_interaction。

  对第 k 个 interaction，会生成一个 step 样本：

  - prefix_messages
    = 当前步之前的全部历史
  - target_message
    = 当前步 assistant 的输出
  - metadata
    = 原始命令等补充信息

  所以：

  一条 trajectory 会拆成多条 step 样本。

  ———

  ### 第 3 步：怎么得到 prefix_messages

  看这个函数：

  - process_data/trajectory_coldstart/stepify.py:20

  它做两件事：

  1. 如果消息是 system 或 user，就原样保留 role 和 content
  2. 如果消息里带 tool_result，就转成：

  {
    "role": "tool",
    "tool_call_id": "...",
    "content": "清洗后的工具输出"
  }

  这里的“清洗”是通过：

  - process_data/trajectory_coldstart/common.py:23

  来做的，主要去掉：

  - ANSI 控制符
  - \x1b[?2004l
  - 一些终端残留

  ———

  ### 第 4 步：怎么得到 target_message

  看：

  - process_data/trajectory_coldstart/stepify.py:40

  它把当前 interaction 的 response 转成：

  {
    "role": "assistant",
    "content": "...",
    "tool_calls": [...]
  }

  其中 tool_calls 通过：

  - process_data/trajectory_coldstart/common.py:94

  被统一成这种结构：

  {
    "id": "...",
    "type": "function",
    "function": {
      "name": "...",
      "arguments": "JSON字符串"
    }
  }

  所以 raw step 里的 target_message 本质上就是：

  “当前这一步 assistant 真正输出了什么。”

  五、canonical 中间样本 是怎么从 raw 中间样本 来的
  核心函数在：

  - process_data/trajectory_coldstart/canonicalize.py:429

  流程是：

  1. 先看 prefix 里的 assistant tool calls 能不能映射
  2. 再看 target 能不能映射
  3. 如果都能映射，就生成 canonical sample
  4. 如果不能，就 drop 并记录原因

  ———

  ### 第 1 步：assistant tool call 怎么 canonicalize

  看：

  - process_data/trajectory_coldstart/canonicalize.py:411

  它会遍历一条 assistant message 里的每个 tool call，然后对每个 tool call 调：

  - process_data/trajectory_coldstart/canonicalize.py:372

  ———

  ### 第 2 步：tool call 怎么变 canonical

  canonicalize_tool_call 做的是：

  1. 先看 tool 名字是不是 task_done
      - 如果是，直接映射成 task_done
  2. 如果不是 task_done，那必须是 bash
      - 否则 unsupported_source_tool
  3. 解析 arguments
      - 它期待里面有 command
  4. 拿到 command 后，调用：

  - process_data/trajectory_coldstart/canonicalize.py:228

  ———

  ### 第 3 步：find | grep | head 怎么被拆开

  这个就是你最关心的。

  先用：

  - process_data/trajectory_coldstart/canonicalize.py:28

  把命令拆成 segment。

  例如：

  find /workspace -type f -name "*.py" | grep -E "(ssl|cert|tls)" | head -20

  拆成：

  1. find /workspace -type f -name "*.py"
  2. grep -E "(ssl|cert|tls)"
  3. head -20

  ———

  ### 第 4 步：第一个 segment 决定主工具家族

  在 process_data/trajectory_coldstart/canonicalize.py:234 以后，它看第一个 segment：

  - 如果第一个是 find
      - 走 find 分支
  - 如果是 grep
      - 走 grep 分支
  - 如果是 sed
      - 走 sed 分支
  - 以此类推

  对于这条命令，第一个是 find，所以进入：

  - process_data/trajectory_coldstart/canonicalize.py:238

  ———

  ### 第 5 步：参数是怎么提出来的

  #### find 部分

  通过：

  - process_data/trajectory_coldstart/canonicalize.py:93

  得到：

  - root_path = /workspace
  - glob = *.py
  - case_insensitive = false

  #### grep 部分

  然后进入：

  - process_data/trajectory_coldstart/canonicalize.py:141

  因为第二段是 grep -E "(ssl|cert|tls)"

  所以得到：

  - pattern = "(ssl|cert|tls)"
  - is_regex = true
  - case_insensitive = false

  在 find 分支里，这些 grep 信息不会变成新的主工具，而是附着到 repo_find_files 上，作为过滤条件：

  - name_pattern
  - filter_is_regex
  - filter_case_insensitive

  #### head 部分

  最后第三段 head -20 用：

  - process_data/trajectory_coldstart/canonicalize.py:53

  - max_lines = 20

  在这个分支里，它被重命名为：

  六、为什么有些 sample 会 drop
  这个是由 process_data/trajectory_coldstart/canonicalize.py:429 决定的。

  drop 有两类主要原因。

  ### 1. prefix 里有历史 assistant tool call 映射失败

  在这里：

  - process_data/trajectory_coldstart/canonicalize.py:438

  如果 require_mapped_prefix=True，而 prefix 中某条 assistant message 不能 cleanly canonicalize，就直接：

  - reason = unmapped_prefix

  这是当前最大 drop 来源。

  ———

  ### 2. target_message 本身映射失败

  在这里：

  - process_data/trajectory_coldstart/canonicalize.py:444

  如果 target 的 raw bash 超出当前支持的规则，就 drop。

  原因可能是：

  - unsupported_shell_control
  - unsupported_command_family
  - grep_parse_failed
  - unsupported_find_pipeline
  - 等等

  ———

  七、step_level_examples_preview.json 里的 dropped_examples 是怎么来的
  这个不是某个现成函数自动产出的，而是我额外跑了一段脚本做的：

  逻辑是：

  1. 遍历 raw 中间实验样本里的每一条 sample
  2. 调一次：
      - canonicalize_sample(sample, require_mapped_prefix=True)
  3. 如果返回 None
      - 说明会被 drop
  4. 对每一种新的 reason
      - 保存一条代表样本

  所以 dropped_examples 的价值是：

  它不是“所有丢弃样本列表”，而是“每种丢弃原因的代表样本”。

  ———
